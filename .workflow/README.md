# .workflow — lead-epic / lead-issue automation

A PM-driven development workflow. **Claude is the PM** (decides direction, orchestrates, judges); **Codex runs the fresh-eyes work** (decomposition review, plan review, implementation, PR review) as independent processes that share no context with the PM. Adapted from a Jira-based design to **GitHub issues** on `NJ97S/personal-blog`.

Two levels: `lead-epic` turns a requirement into a **milestone + issue DAG**; `lead-issue` drives **one issue** of that DAG to merge.

## The six skills (`.claude/skills/`)

| Skill | Runs on | Role |
|-------|---------|------|
| `lead-epic` | Claude (main session) | Epic PM. Crystallize requirement → design → decompose into an issue DAG → create milestone + issues. |
| `review-decomposition` | Codex (spawned) | Puts the epic's issue DAG on trial (coverage, dependencies, scope conflicts, sizing) before issues are created. Verdict: PASS / REVISE / RETHINK. |
| `lead-issue` | Claude (main session) | Issue PM. Owns the 9-phase lifecycle for one issue. Writes **no** implementation code. |
| `review-plan` | Codex (spawned) | Front gate. Puts the plan on trial against the codebase before any code is written. Verdict: PASS / REVISE / RETHINK. |
| `developer` | Codex (spawned) | Implements the plan in a worktree; writes all code + a report. |
| `review-pr` | Codex (spawned) | Fresh-eyes PR reviewer. Every finding is blocking. Verdict: APPROVE / REQUEST_CHANGES. |

Plus one helper: **`workflow-guide`** (Claude) — `/workflow-guide` regenerates a readable overview of all the skills (from their SKILL.md, so it never drifts) into `docs/guide.md` + HTML.

## How to run

```
/lead-epic "<requirement>"     # scope a feature into a milestone + issue DAG
/lead-issue <issue-number>     # drive one issue (a DAG node) to merge
```

`lead-epic` runs 8 phases (⛔ approval gates: crystallized requirement, and before creating anything on GitHub) and hands off the topological `/lead-issue` order. `lead-issue` then walks its 9 phases, pausing at four gates: **scope fence**, **final plan**, **push**, **merge**. Epics are represented as **milestones**; an issue with no milestone is treated as standalone.

## The meshed review loop

```
PM writes plan ─► review-plan tries the plan ─► PM verifies each finding, revises/rebuts ─► (loop to PASS)
                                                                                              │
PM spawns developer (worktree) ─► reads report ─► PM opens PR (after approval)                │
                                                                                              ▼
review-pr posts REQUEST_CHANGES ─► PM: reviewer-right → directive → developer fixes           
                                       developer-right → 3-part rebuttal comment              
                                   └─► review-pr RE-REVIEW adjudicates rebuttals ─► (loop to APPROVE) ─► merge
```

`review-plan` catches direction errors *before* wasting a developer run; `review-pr` judges the *result*.

## Scripts (`.workflow/bin/`)

- **`spawn-agent.sh --skill <name> [--cd <dir>] [--model <m>] --args "<...>"`**
  Spawns a fresh Codex process that follows `.claude/skills/<name>/SKILL.md`. Prints the path to the agent's final message. Runs Codex with `--dangerously-bypass-approvals-and-sandbox` so it can use `gh`/`git`/`npm` unattended — use only in a trusted local checkout.
- **`gh-review-as-bot.sh <repo> <pr> [result-json]`**
  The only sanctioned way to post a PR review (skills never call `gh pr review` directly). Reads `{ "verdict", "body" }` from the result JSON.
- **`render-doc.sh <file.md | dir>`** (wraps `render-doc.mjs`)
  Renders Markdown docs to sibling `.html` using the project's own remark/rehype packages (no new dependency, offline). Markdown is the source of truth; HTML is derived and gitignored. Mermaid diagrams render client-side (needs network when the HTML is opened). Open rendered HTML in the external Chrome browser: `open -a "Google Chrome" <file>.html`.

## Documentation (`.workflow/docs/`)

Each unit of work gets **one folder** holding all its docs. Markdown is committed (the source of truth); the sibling `.html` views are gitignored and regenerated by `render-doc.sh`.

```
docs/
  epics/<slug>/                 # one lead-epic run
    design.md   review.md   index.md
  issues/<N>-<slug>/            # one lead-issue run
    plan.md   plan-review.md   report.md
    directive-r<k>.md   pr-review-r<k>.md   index.md
```

- `<slug>` — short ASCII kebab-case summary; `<N>` — GitHub issue number.
- Every gate's output is preserved as a doc: plan + its review, the implementation report, each fix directive, and each PR-review round.

Other run state (gitignored): `tmp/` (spawn logs + last-message files) and `.review-result.json` (latest review verdict/body).

## Posting reviews & the bot identity

GitHub forbids a PR **author** from submitting a formal APPROVE / REQUEST_CHANGES review on their own PR. So `gh-review-as-bot.sh`:

- With **`BOT_TOKEN`** set (a PAT for a separate account, or a GitHub App token) → posts a **formal review** as that identity.
- Without it → posts the verdict + body as a **PR comment** (works on your own PR; the verdict stays machine-readable in an HTML comment header).

To get true bot-authored reviews, create a bot account or App, then `export BOT_TOKEN=...` before running.

## Local-only by design (no CI, no extra billing)

This workflow runs **entirely on your machine** on subscriptions you already have:

- **Claude (PM)** runs in Claude Code.
- **Codex (fresh-eyes reviewers + developer)** runs locally via `codex exec`, authenticated with **Sign in with ChatGPT** (`codex login`) — so it draws on your ChatGPT subscription, **not** a pay-as-you-go OpenAI API key.

There is intentionally **no GitHub Actions / CI** here. Auto-running `review-pr` in CI would need headless Codex auth, and the only robust headless path is a paid `OPENAI_API_KEY` (platform.openai.com, billed separately from a ChatGPT subscription). That extra billing is deliberately avoided. `review-pr` is therefore triggered from the PM loop (Phase 8) or run manually, always locally.

If you ever want CI later, add a workflow that authenticates Codex with a secret and runs `spawn-agent.sh --skill review-pr --args "$REPO $PR"`, posting via `gh-review-as-bot.sh` with `BOT_TOKEN=$GITHUB_TOKEN`. Not enabled by choice.
